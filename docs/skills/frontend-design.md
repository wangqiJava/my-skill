# frontend-design

`frontend-design` 是 Anthropic 维护的前端设计指导 Skill。它要求 Agent 先理解产品主题、受众和页面任务，再选择有辨识度的视觉方向，最后把设计计划落成 HTML、CSS、JavaScript、React 或 Vue 代码。

它的重点不是套一套“好看的组件”，而是让每个项目的配色、字体、空间关系、动效和文案都服务于同一个主题。这篇记录根据 [skills.sh 的 frontend-design 页面](https://www.skills.sh/anthropics/skills/frontend-design) 与上游公开文件整理；本地完整实战案例仍需单独补录。

## 它解决什么

很多界面的问题不是“少一个按钮”，而是页面没有明确的性格：字体随便选，卡片到处复制，颜色只剩一套默认渐变，动效也没有表达内容。`frontend-design` 把视觉设计当成一组需要解释的决策，要求在写代码前回答：

- 这个产品或页面属于什么主题、行业和材料语汇？
- 页面面对谁，最主要的任务是什么？
- 哪个元素应该成为记忆点，哪些部分需要安静退后？
- 字体、颜色、布局和动效怎样共同表达这个主题？
- 在手机、键盘操作、减弱动效和低对比环境下是否仍然可用？

它适合新页面、首页 Hero、营销页、后台界面和已有页面的视觉重塑，也适合在写代码前校准审美方向。纯数据处理、接口重构或一眼就能完成的文字修正，不需要先走完整的设计流程。

## 设计工作法

### 1. 先落到真实主题

如果需求没有写清产品是什么，先提出一个具体的主题、受众和页面主要任务，再向用户确认。视觉来源应来自产品真实的行业、材料和语汇，而不是从一组抽象的“高级感”关键词开始。

### 2. 先写短设计计划

开始编码前先做一页紧凑的设计计划，至少包含四部分：

| 部分 | 要回答的问题 |
| --- | --- |
| 色彩 | 用 4–6 个有名字的色值描述基础色、文字色、强调色和状态色。 |
| 字体 | 选什么字体，各自负责标题、正文、数据或操作文字？ |
| 布局 | 页面如何分区、如何对齐、哪里留白，是否需要用 ASCII 草图比较方案？ |
| 原则 | 这个页面凭什么与同类界面不同，哪个元素是唯一的记忆点？ |

### 3. 对照 brief 做一次反模板检查

把计划重新读一遍，问自己：如果换一个相似需求，我是不是还会给出同样的暖米色、衬线标题、圆角卡片和渐变？如果答案是“会”，就回到主题和受众，修改那些没有来自本项目的默认选择。需求明确指定的风格优先级最高；只有没有被需求占用的自由，才需要主动避开常见默认。

### 4. 再写代码

实现时保持 CSS 选择器的层级清楚，避免通用类和元素选择器互相覆盖 padding、margin 或颜色。设计计划确定的是方向，不是让所有区块都变得复杂；代码应匹配这套审美真正需要的复杂度。

### 5. 构建后自我批评

用截图检查成品，尤其看首屏、移动端、键盘焦点和空状态。大胆的设计集中在一个记忆点上，其余内容保持克制；删掉只为装饰、没有传达信息的线条、标签和动画。

## 关键设计原则

### Hero 是第一句

首屏应该先展示主题世界里最有代表性的内容，可以是标题、图片、动画、实时演示或一个可操作的瞬间。不要因为“首页都要有大数字、渐变和统计卡片”就照搬，它们只有在确实服务于页面任务时才值得使用。

### 字体是界面性格

字体不只是承载文字的容器。选一到两套有明确分工的字体，建立稳定的字号、字重、宽度和字距层级。正文默认控制在较短的行长内；衬线正文可以略长，但要给足行高。标题的字形和排版本身也应参与视觉表达。

### 结构要传达信息

边框、编号、眉题、分隔线和标签都应该编码真实结构，而不是填空装饰。只有内容确实是顺序、流程或时间线时，才使用 `01 / 02 / 03` 这类编号。

### 动效要回答动作

非用户触发的动效应少而明确，一次编排好的首屏展开或内容揭示，通常比每个区块都淡入上移更有力。用户点击、展开、确认后产生的动效可以保留，但要让人看得出发生了什么变化。

### 文案是内容，不是装饰

从用户角度命名功能，用简单、具体的词描述它是什么或会做什么。按钮直接写结果，例如“保存修改”，不要写模糊的“提交”。同一个动作在按钮、提示和完成状态里保持同一套词汇。

错误和空状态也要提供方向：说明发生了什么、用户下一步可以怎么处理，避免含糊的道歉和没有行动入口的空白页。整体语气使用主动语态、完整句子和与品牌匹配的口吻。

## 需要主动检查的通用默认

这些风格并非绝对不能用，但不应在没有理由时自动套用：

- 暖米色底、衬线大标题和陶土色强调色的组合
- 纯黑底配单一荧光绿或朱砂色
- 报纸式细线、零圆角和密集多栏
- 所有内容都做成相同圆角、相同阴影的 SaaS 卡片
- 每个标题上方都放全大写眉题，所有链接都加箭头
- 中间点串联所有元信息，或用等宽字体装饰小标签

检查的目标不是反对这些风格，而是确认它们来自当前 brief，而不是因为模型对相似页面形成了惯性。

## 实际用法

### 输入示例

```text
请用 frontend-design 先为“拾墨手记”首页做设计计划，不要直接写代码。

主题：个人技术手记与知识归档，气质安静、克制，有中式手札的材料感。
用户：需要快速找到项目、Skill 和工具记录的开发者。
任务：首屏让人理解站点是什么，并能继续进入三类记录。
约束：桌面和手机都要稳定，保留搜索和深色模式，尊重键盘焦点与 prefers-reduced-motion。

请先输出 4–6 个颜色 token、字体角色、布局草图和设计原则；
然后检查这套方案有没有落入通用 AI 页面默认，说明你改了什么以及为什么。
确认计划后再实现。
```

### 期望输出

一次完整工作应至少留下：

1. 与主题和受众对应的视觉方向，而不是泛化的“高级感”。
2. 颜色、字体、布局和原则组成的 token 计划。
3. 设计方案和 brief 的对照检查，以及主动删除或修改默认做法的理由。
4. 可运行的前端实现，包含响应式、可见焦点、减弱动效和基本视觉可访问性。
5. 截图或实际页面检查后的问题清单，而不是只凭代码判断完成。

## 踩坑与解决

- **先堆装饰再找主题。** 先确定产品、受众和主要任务，视觉才有来源。
- **把“独特”理解成所有地方都用强效果。** 把大胆程度集中在一个记忆点，其余层级保持安静。
- **复制组件库的统一圆角卡片。** 层级不同的内容需要不同的空间和结构，不要让同一种卡片承担所有信息。
- **每个区块都加入场动画。** 只保留能表达内容变化的动效，并尊重 `prefers-reduced-motion`。
- **只检查桌面首屏。** 还要检查移动端、键盘焦点、错误和空状态。
- **用营销话术代替导航文案。** 操作文字要说明用户会得到什么结果，避免聪明但不清楚的词。

## 使用心得

这套 Skill 最有价值的部分是把“审美”变成一份可复查的计划：颜色、字体、布局和原则都有来源，写代码前还要主动检查是否只是重复模型常见的页面。它并不替设计师做最终判断，主题是否真的贴合产品、文字是否适合目标用户、对比度和键盘路径是否足够，仍需人工验证。

建议每次使用后记录三件事：最终保留的记忆点、删掉的默认装饰、截图检查发现的问题。下一次设计同类页面时，这些记录比再收集一组灵感关键词更有用。
